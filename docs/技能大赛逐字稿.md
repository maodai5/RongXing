## 一、开场：项目一句话 + 我的分工（约 30 秒）

各位评委老师好。我们的作品叫**绒星 RongXing**，一个面向猫主人的健康管理 App：给猫咪建档、生成会动的数字分身，用规则引擎做健康初筛，再用 AI 陪伴日常。

我们是一个团队分工协作：移动端和产品交互由队友负责。**我负责整个后端**——从 API 设计、数据建模、规则引擎，到异步任务和安全体系，最后用 Docker 把全部服务容器化部署。下面重点讲后端。

## 二、后端架构：分层设计与技术选型（约 1 分钟）

后端技术栈是 **Python 3.12 + FastAPI + SQLAlchemy 2 + Alembic + MySQL 8**，代码按职责分成五层：`routers` 接口层、`schemas` 请求校验层、`models` 数据模型层、`services` 业务逻辑层、`providers` 外部 AI 服务适配层。

为什么选 FastAPI？三个理由：

第一，**类型安全从入口开始**。每个接口的入参出参都由 Pydantic 定义，非法数据在进业务逻辑之前就被拦截，同时自动生成 OpenAPI 文档，前后端联调不用口头对字段。第二，**原生异步**。我们后端要调四类大模型服务，生图、生视频动辄几十秒，异步框架保证一个慢请求不拖垮整个服务。第三，性能上它基于 Starlette + uvicorn，在 Python 框架里属于第一梯队。

后端十三个路由模块对应十三个业务域，架构上刻意做到了**一层只做一件事**：接口层不写业务，业务层不碰 HTTP，模型层不依赖框架——这样任何一层替换实现都不牵连其它层。

## 三、数据建模与迁移：Alembic（约 40 秒）

数据库 **25 张表**，覆盖用户、宠物档案、健康记录、异步任务等域。密码不落明文，用 **argon2id** 哈希——它是 2015 年密码哈希竞赛冠军算法，抗 GPU 爆破强于 bcrypt；登录态用 JWT。

工程上最关键的决策是**全量 Alembic 版本化迁移**：每次改表结构都是一个带版本号的迁移脚本。任何一台机器从零拉起，跑一遍 `alembic upgrade head` 就能得到结构完全一致的数据库——这一条直接支撑了后面的 Docker 一键部署，也是团队协作时"我的库和你的库不一样"这个经典问题的根治方案。

## 四、亮点设计：规则引擎给 AI 划边界（约 1 分钟）

后端最有代表性的设计是**规则引擎和大模型的分工**。

健康初筛不靠大模型，靠我们自己写的**规则引擎**：规则全部放在版本化的 **YAML 规则包**里，比如"24 小时未进食，叠加体重骤降超过 10%，触发红线"。红线情况**完全不经过大模型**，直接下发就医引导卡。为什么？因为医疗红线必须**确定性、可解释、可审计**——大模型输出有随机性，同一个症状今天报红线明天不报，是产品事故；而 YAML 规则可以做版本管理、代码评审和回归测试。

那 AI 用在哪？`providers` 适配层对接阿里云 DashScope 四个模型：**qwen-image-edit** 生成猫咪数字分身，**wanx2.1 图生视频**让形象动起来，**qwen-max / qwen-plus** 做每猫独立会话、20 条上下文的陪伴聊天，**qwen2-audio** 解读猫叫声。聊天里同样有红线兜底：命中红线关键词的消息**零 LLM 调用**，直接转就医引导——省钱、省时、更安全。

【可删】把外部 AI 收敛在 providers 一层还有个好处：换模型供应商只改适配层，业务代码一行不动。

## 五、可靠性：异步任务与幂等设计（约 1 分钟）

生图生视频都是长耗时操作，我们用 **Redis 7 + arq** 做异步队列：API 收到请求只负责落库和入队，立刻返回任务 ID；worker 容器异步消费，生成结果落对象存储。

这条链路有三个可靠性设计：

第一，**数据库是任务与状态的唯一事实源**。Redis 只做调度不做存储，就算gRedis 数据全丢，任务状态从数据库照样恢复，不会出现"任务凭空消失"。

第二，**幂等键去重**。移动端做了浅离线，断网时记录进本机队列，恢复后带原幂等键补发；服务端靠幂等键去重，重试十次也只写一条，弱网环境数据不重复。

第三，**失败重试带退避和死信**。生成失败的任务按策略退避重试，超过上限进入可人工介入的失败状态，不无限占用资源。

## 六、重点：Docker 容器化部署（约 1 分半）

部署是我负责部分里工程化程度最高的，详细讲。

**为什么用 Docker？** 后端有 MySQL、Redis、API、worker 四个角色，手装一遍环境半小时起步，还容易"在我机器上是好的"。Docker 把环境变成代码：`docker compose up --build -d` 一条命令，任何机器五分钟拉起完整系统，评委现在就能复现。

**怎么编排的？** docker-compose 定义五个服务：`mysql:8.4` 强制 utf8mb4 字符集，保证 emoji 昵称和中文不乱码；`redis:7` 开 AOF 持久化；`migrate` 独立容器跑数据库迁移；`api` 和 `worker` 是业务容器。

三个工程细节，是踩坑之后才做对的：

第一，**启动顺序用健康检查锁死**。MySQL 和 Redis 配了 healthcheck，migrate 声明"等 MySQL 健康后才执行"，api 和 worker 声明"等 migrate **成功完成**才启动"——用的是 Compose 的 `service_completed_successfully` 条件。这杜绝了"API 起来了但表还没建好"的竞态，也让迁移失败时整个栈起不来、快速暴露问题，而不是带着旧表结构悄悄运行。

第二，**一份环境配置，两种网络形态**。开发时连 `127.0.0.1`，容器里这个地址不通。我写了 docker-entrypoint 脚本，容器启动时用 MYSQL\_* 变量动态拼出 `mysql:3306` 连接串。开发者和容器共用**同一份 .env**，配置永不漂移。

第三，**数据卷持久化 + 最小暴露面**。MySQL 和 Redis 数据落在命名卷，容器删除数据不丢；对外只暴露 API 的 8000 端口，数据库和缓存只在容器网络内可达，攻击面最小。

【如果评委追问】Dockerfile 基于 `python:3.12-slim`，依赖按 requirements.txt 锁版本安装，利用分层缓存，改代码不用重装依赖。

## 七、质量保障与收尾（约 40 秒）

后端**pytest 400+ 用例**，覆盖规则引擎、鉴权、幂等队列、权重计算这些核心模块，全部通过才算完成。规则包本身也有针对性测试——改一条红线规则，测试会立刻告诉你影响了哪些用例。

总结一下我负责的后端：**FastAPI 分层架构**保证类型安全和职责清晰，**Alembic 迁移**让数据库结构可演进、可复现，**YAML 规则引擎给 AI 划出安全边界**，**Redis 队列 + 幂等键 + 唯一事实源**保证弱网和故障下的数据一致性，最后**Docker Compose 把五个服务收敛成一条命令**。

我的原则是：每一项技术选择都必须对应一个真实问题。后端就是这么做的，谢谢评委老师，欢迎提问。

## 附：评委可能追问的问题与答法（后端向）

**Q：为什么 MySQL 而不是 PostgreSQL / MongoDB？**  
健康记录是强关系型数据（用户-宠物-记录-任务），需要事务和外键约束；MySQL 8 生态成熟，utf8mb4 对 emoji 昵称友好。MongoDB 在多表关联统计场景反而要靠应用层拼。

**Q：规则引擎为什么不用大模型直接判断？**  
医疗红线要求可解释、可复现、可审计。大模型有随机性，而且慢、贵；YAML 规则可版本管理、可灰度，红线响应还是毫秒级。

**Q：JWT 的缺点？**  
无法主动作废。所以做了协议版本化与服务端凭证校验，注销走 15 天冷静期后物理清除。

**Q：为什么迁移是独立容器而不是 API 启动时跑？**  
迁移和业务进程生命周期应该分开：迁移失败必须 fail fast，整个栈起不来，而不是 API 带着旧表结构悄悄服务。

**Q：worker 挂了任务会丢吗？**  
不会。任务状态以数据库为唯一事实源，arq 只是调度层；worker 重启后从数据库恢复未完成任务，重试带退避策略。

**Q：怎么防止 AI 接口被刷 / 配额滥用？**  
services 层有配额管理，按用户限制 AI 生成调用；红线分流本身也省掉了大量 LLM 成本。

**Q：argon2id 相比 bcrypt 的优势？**  
内存硬设计，抗 GPU/ASIC 并行爆破；时间、内存、并行度参数可调，可随硬件升级平滑加强。
